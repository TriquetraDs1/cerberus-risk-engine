## 1. What Cerberus is, in one paragraph

A transaction-risk engine built around one thesis: static fraud thresholds get
reverse-engineered by fraud rings within weeks, so a model that only reports
precision/recall on a public dataset has never proven it survives an adaptive adversary.
Cerberus scores individual transactions with a cost-sensitive model, detects coordinated
rings with an entity-link graph, and then **red-teams itself** — a synthetic adversary
searches for evasions, we measure how far recall drops under each attack, we retrain, and
we prove the recovery. That closed loop, with a before/attack/after number, is the
submission. The classifier is table stakes; the loop is the differentiator.

**Scope guardrail (state this the same way every time):** defensive-only research project.
The adversarial harness attacks *only its own sandboxed synthetic model* to generate
hardening data for that same model. No real-world evasion tooling, no code targeting
Razorpay or any third party, no exploit code. Every dataset is public (Kaggle) or
generated by this repo's own generator.

## 3. What's built — components and their real numbers

Every number below is read live from `reports/*.json`, regenerated by the pipeline.
Nothing here is aspirational.

### Synthetic data + ring injection — `src/cerberus/data/synthetic_rings.py`
- 60,565 transactions, ~1.8% base fraud rate modulated per segment.
- 25 injected coordinated rings with ground-truth membership.
- 75 innocent household entity-sharing pairs (accounts that legitimately share a device),
  so the ring detector's false-positive rate can be measured honestly rather than assumed
  to be zero.
- 4 merchant segments (grocery / electronics / digital / travel) with genuinely different
  amount distributions and fraud economics — segment is a real risk signal, not plumbing.

### Point-risk model — `src/cerberus/detection/point_risk.py`
- LightGBM (falls back to sklearn `HistGradientBoostingClassifier` if unavailable).
- **ROC-AUC 0.80, PR-AUC 0.30** on a chronological three-way split (train 64% / calibration
  16% / test 20%). Splits are time-based everywhere — never random — because rings cluster
  in time and would leak across a random boundary.
- 12 features: 8 behavioural (amount, amount z-score, 1h velocity count/amount, hour,
  off-hours flag, day-of-week, entity degree) + 4 one-hot segment columns. `FEATURE_COLUMNS`
  in `features/pipeline.py` is the single source of truth for this schema.

### Probability calibration — `src/cerberus/detection/calibration.py` *(beyond original scope)*
- Isotonic regression on the held-out calibration split.
- **Brier score 0.0645 → 0.0164. Expected calibration error 0.140 → 0.003.**
- Why it was needed: `class_weight="balanced"` skews raw LightGBM scores away from true
  P(fraud); calibration closes that gap so `risk_score` is an actual probability the
  decision layer can reason about, not just a ranking.

### Ring detector — `src/cerberus/detection/ring_detector.py`
- Entity-link graph (shared device / IP / card / address) + Louvain community detection.
- **25/25 injected rings recovered (100% mean recovery).**
- **9.3% false-positive rate** (7 of 75) on innocent household device-sharing — reported,
  not hidden. This is the honest FP-cost story for the graph layer.
- Louvain over a GNN is deliberate: explainable, fast to validate against ground truth,
  and feasible for a solo 10-day build. GNN is named as the production path.

### Decision layer — `src/cerberus/decision/cost_matrix.py` *(Day 4)*
- Per-segment cost matrices — each segment's FP and FN cost is derived from its own mean
  transaction amount plus a documented retention-sensitivity multiplier, not one global
  FP:FN assumption.
- 3-way routing (approve / review / block) per segment.
- **Segmented routing costs 10.7% less** than applying one global threshold everywhere.
  The saving is concentrated in `travel_luxury` (27% cheaper — high ticket size, so a
  missed fraud is expensive and a tighter threshold pays off) and near-zero in
  `electronics_highvalue` (the global threshold was already close to that segment's
  optimum). That spread is the point: one threshold is wrong in different directions for
  different segments.

### Adversarial hardening harness — `src/cerberus/adversarial/` *(Days 5–6, the differentiator)*
Three evasion strategies, each found by an adaptive local hill-climb against the live
model (not a fixed script): **structuring** (split a large amount into many sub-threshold
transactions), **identity rotation** (spread the ring across more devices so the graph
never forms a dense community), **slow ramp** (stretch the burst so velocity features
never trigger). Combined detection score, from `reports/adversarial_hardening_report.json`:

| Strategy | Unattacked | Under attack | After hardening | Net recovery |
|---|---|---|---|---|
| Structuring | 1.00 | 0.51 | 0.92 | **+0.42** |
| Slow ramp | 1.00 | 0.55 | 0.86 | **+0.31** |
| Identity rotation | 1.00 | 0.33 | 0.47 | +0.14 |

- Structuring and slow-ramp harden well — they degrade *point-risk* features (amount,
  velocity) that retraining can learn from.
- **Identity rotation barely recovers, and that is reported as an open limitation, not
  patched over.** It attacks the Louvain ring detector specifically, and Louvain is
  unsupervised — retraining the point-risk model cannot teach a community-detection
  algorithm anything. The honesty of this limitation is a stated strength of the
  submission. Do not "fix" it by quietly tuning Louvain parameters to hide the number.
- The regression gate (`--min-recovery`) runs in CI on every push, so a change that
  weakens hardening fails the build.

### Serving API — `src/cerberus/serving/app.py` *(Day 7)*
- FastAPI `POST /score` — serves the hardened model by default, computes features in-process
  (per-account velocity history), applies segment-aware 3-way routing, returns SHAP-derived
  `reason_codes` and a `cost_basis` block.
- `/health`, `/metrics` (Prometheus), structured JSON logs, SQLite append-only audit log
  (`/audit/recent`).
- **Graceful degradation as a real code path, not a README claim:**
  `POST /admin/graph-status?status=degraded` flips the graph service to unavailable and
  `/score` keeps serving decisions with `ring_check: "unavailable"` instead of crashing.
  This is the failure-and-recovery moment for the demo video.

### Dashboard — `dashboard/` (Next.js) *(+ case management beyond scope)*
- Four pages: Review Queue, Ring Network, Adversarial Hardening (the before/attack/after
  chart — the strongest 30 seconds of the demo), System Health (reliability diagram).
- **Case-management workflow:** escalate or dismiss a detected ring from its side panel,
  mark a transaction reviewed from its drawer, and the action persists server-side across
  reloads. Turns the dashboard from a viewer into something an analyst works in.
- `scripts/export_dashboard_data.py` reads the actual trained model, calibrator, SHAP
  explainer, Louvain output, and adversarial report off disk and writes the JSON the
  dashboard renders. Zero mock data anywhere.

### Plain-English narration — `src/cerberus/llm/` *(Day 8, A1)*
- Every queued decision (`queue.json` `explanation` field) and the new
  `GET /explain/{transaction_id}` API endpoint carry a 2–3 sentence summary of *why*
  the pipeline reached that decision, assembled from that decision's own reason codes,
  risk score, ring linkage, and segment cost basis.
- **It describes deterministic output; it never re-scores.** The structured
  `reason_codes` remain authoritative — the summary is an additional field, and
  `/explain` echoes the reason codes back so the prose can be checked against them.
- Uses Claude (`claude-haiku-4-5`) when `ANTHROPIC_API_KEY` is set; a deterministic
  templated sentence built from the same fields otherwise. `anthropic` is an optional
  install (`pip install -e ".[llm]"`), imported lazily — the pipeline, the dashboard
  export, and CI all run green with no key and no network. A failed LLM call falls back
  to the template rather than breaking the caller.
- 9 tests in `tests/test_llm.py` pin the templated path (the one CI runs); 2 in
  `tests/test_serving.py` cover the `/explain` endpoint.
- **What's still stretch:** A2 (chargeback dispute drafting) and A3 (analyst copilot) —
  see `IMPLEMENTATION_ROADMAP.md` Phase 1.

### Reproducibility
- `Dockerfile` (two-stage: `pipeline` target and `serving` target), `docker-compose.yml`.
- Deterministic given a fixed `CERBERUS_RANDOM_SEED`.
- Runnable by a reviewer in under five minutes.

## 4. Issues faced and how they were resolved

A short engineering log — the non-obvious ones, worth having ready if asked "what was hard".

| # | Issue | Root cause | Resolution |
|---|---|---|---|
| 1 | Dashboard hydration error on SVG tooltips | React treats a `<title>` tag as special regardless of SVG namespace; interpolated JSX children in it break hydration | Replaced with a non-`title` tooltip element |
| 2 | Ring graph silently rendered with **zero edges** (every edge dropped) | `d3-force`'s `forceLink().id()` mutates `link.source` / `link.target` from strings into node object references after the simulation runs; downstream code still expected strings | Read the ids back off the mutated objects after simulation, not before |
| 3 | Hydration mismatch on dates | Node and browser disagree on ICU locale defaults, so server and client rendered different date strings | Hand-rolled date formatting, no locale dependency |
| 4 | Production build would have served **stale case-action state** | Review Queue and Ring Network were statically prerendered at build time despite reading a mutable local JSON file — a deployed escalate/dismiss would never have appeared without a full rebuild | `export const dynamic = "force-dynamic"` on those two routes; caught by running an actual `next build`, not `dev` |
| 5 | Calibration cost some ROC-AUC | Carving a disjoint calibration split out of training data leaves the model less data to learn from | Accepted and documented as a deliberate trade-off — a calibrated 0.80 is more useful than an uncalibrated 0.82 |
| 6 | `CalibratedClassifierCV(cv="prefit")` is deprecated in sklearn 1.6 | API removal | Hand-rolled isotonic map (one function) — which is what that method did internally anyway |
| 7 | `test_serving.py` failed on a fresh clone | The serving tests need a trained model on disk | Tests skip gracefully when `models/` is empty, rather than failing |
| 8 | Identity rotation would not harden | Louvain is unsupervised; there is nothing to retrain | Not resolved — reported as an open limitation in `MODEL_CARD.md` and `docs/ARCHITECTURE.md`. This is a deliberate choice, not an omission |

**Known seam (not a bug):** the case-action store is a file (`dashboard/data/case_actions.json`,
gitignored), separate from the Day 7 SQLite audit log. Noted in `lib/caseActions.ts` as
something to unify later.

## 6. How this positions you

**What the submission demonstrates to a fraud/risk panel:**

1. **You understand the actual lifecycle a fraud team lives in** — not "train a classifier,
   report AUC," but build → attack → measure decay → retrain → prove recovery → gate it in
   CI so it can't regress. Most submissions in this category stop at the classifier.
2. **You report cost, not vanity metrics.** Every number ships with its false-positive
   cost. The decision layer is cost-optimised per segment, not accuracy-optimised. This is
   the language a risk org actually speaks.
3. **You state limitations before you're asked.** Synthetic data, a scripted adversary, an
   un-hardenable graph layer under identity rotation — all named up front. On a panel,
   pre-empting the pushback reads as senior; hiding it and getting caught reads as junior.
4. **You ship enterprise-shaped, not enterprise-cosplay.** FastAPI + SQLite + a batch graph
   rebuild + Prometheus + an audit log + graceful degradation — the shape of a production
   system at a scale that's honest for a solo 10-day build. No Kafka added just to look
   mature.
5. **Your red-team background is load-bearing, not decoration.** The adversarial harness is
   the part of this that a red-teamer builds better than a data scientist, and it's the
   part that's the differentiator.

**How to convert it:**

- **In the video (Days 9–10):** open on the `/adversarial` before/attack/after chart —
  that's the thesis in one image. Then the graceful-degradation demo (flip the graph
  service, watch `/score` keep working). Then the per-segment cost saving. Close on the
  identity-rotation limitation, said plainly — it's a strength that you're the one who
  raised it.
- **Rehearse the two panel questions** in `docs/ARCHITECTURE.md` §7 out loud: "isn't this
  just testing against yourself?" and "Louvain on synthetic data is easy — validated on
  anything real?" Have the honest answer ready, not a defensive one.
- **As a portfolio piece afterwards:** the repo is clean, documented, CI-gated, and
  reproducible in five minutes. It stands on its own in an interview without you in the
  room. The `MODEL_CARD.md` and `docs/ARCHITECTURE.md` are the artifacts that make it
  reviewable by someone senior.
