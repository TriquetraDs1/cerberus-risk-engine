# Cerberus — an adversarially-hardened transaction risk engine

> **Scope and guardrail, stated up front:** Cerberus is a **defensive** fraud-detection
> research project. The "adversarial" component in this repo is a red-team harness that
> attacks **only its own sandboxed synthetic model** to generate hardening data for that
> same model. Nothing in this repo is offense-capable: there is no real-world evasion
> tooling, no code that targets Razorpay or any third-party system, and no exploit code of
> any kind. Every dataset used is either public (Kaggle) or synthetically generated by this
> repo's own generator. If any file here reads as ambiguous on this point, treat this
> paragraph as the authoritative scope statement.

## What this is

A transaction-risk engine built around a simple thesis: static fraud thresholds get
reverse-engineered by fraud rings within weeks. A model that only reports precision/recall
on a public dataset never demonstrates that it survives contact with an adaptive fraud
ring. Cerberus does three things most submissions in this space don't:

1. **Scores individual transactions** with a cost-sensitive point-risk model (not an
   accuracy-maximizing one — a false positive and a false negative do not cost the same,
   and the threshold reflects that).
2. **Detects coordinated fraud rings** via an entity-link graph (shared device / IP / card
   / address) and community detection — not just point-in-time scoring.
3. **Red-teams itself.** A synthetic adversary tries to evade the detector (amount
   structuring, identity rotation, slow-ramp ring behavior), we measure how much recall
   decays under each attack, and we hardened the model in response. That loop, with a
   before/after recall-decay number, is the actual submission — not the classifier.

Named for the three-headed guard dog: three detection layers (point-risk, ring, harness)
guarding one gate.

## Why not just a classifier

See `docs/ARCHITECTURE.md` for the full writeup, but the short version: a tabular
classifier on a public Kaggle dataset is table stakes, not a differentiator. Every honest
metric it produces has already been produced by a hundred tutorials. The differentiator
here is the closed loop — build a detector, attack it, measure the damage, fix it, prove
the fix — because that is the actual lifecycle a production fraud team lives in, and it's
the one thing a red-team background is directly useful for building.

## Quickstart

```bash
python -m venv .venv
source .venv/Scripts/activate   # Windows Git Bash; use .venv\Scripts\Activate.ps1 in PowerShell
pip install -r requirements.txt
pip install -e .

# Day 1-2: synthetic data + baseline point-risk model
python scripts/generate_data.py
python scripts/train_baseline.py

# Day 3: Louvain ring detector, validated against ground truth
python scripts/detect_rings.py

# Export real pipeline output as JSON for the dashboard (no mock data)
python scripts/export_dashboard_data.py
```

Or with Docker: `docker compose up` runs the same pipeline end-to-end into `./data`,
`./models`, `./reports`.

Then the analyst dashboard:
```bash
cd dashboard
npm install
npm run dev   # http://localhost:3000
```

If you drop a Kaggle `creditcard.csv` into `data/raw/`, the loader blends its base rate
into the synthetic generator instead of using a fully synthetic baseline — see
`src/cerberus/data/loader.py`. This is optional; the pipeline runs end-to-end without it.

## Honest limitations (read this before the panel does)

- Fraud rings are synthetic, and the adversary attacking the model is also code we wrote.
  This validates robustness to *known* evasion classes, not a real-world adversarial
  guarantee. A production version needs real labeled fraud and an actual red-team process,
  not a script.
- Louvain community detection is validated against synthetic ground truth; the honest
  false-positive story (legitimate users who share a device, e.g. family members) needs to
  be checked against the non-fraud portion of a real dataset — see `docs/ARCHITECTURE.md`.
- Chargebacks land 30–90 days after the transaction in reality; this repo does not model
  that label lag.
- SQLite, a synchronous API, and a batch-recomputed entity graph are demo-appropriate
  choices, not production-scale ones. See `docs/ARCHITECTURE.md` → Trade-off Analysis for
  what changes at real volume.

Days 1-3 of the 10-day plan are done:

- Baseline point-risk model (LightGBM), cost-sensitive threshold preview

Days 4-10 (cost-matrix decision layer, the adversarial hardening harness, FastAPI
serving, and the submission video) are still ahead — see `docs/ARCHITECTURE.md` for the
full roadmap. The adversarial harness (Day 5-6) is the actual differentiator; nothing
before it should be mistaken for the finished submission.
